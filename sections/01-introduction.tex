\section{Introduction}
\label{sec:introduction}

Conventional unit tests validate software behavior
by checking specific input-output pairs~\cite{orso_2014_software,ammann_2016_intro,myers_2011_art},
but leave most inputs along the same execution path untested.
Property-based testing~\cite{claessen_2000_quickcheck,hughes_2007_quickcheck} instead generates many inputs
and checks whether specified properties hold across executions.
For example, given the $abs$ method in Figure~\ref{fig:regression-detection},
a unit test which asserts that $abs(0)$ returns $0$ would 
still pass after changing \texttt{x >= 0} to \texttt{x == 0}, 
whereas a property-based test which asserts $abs(x) = x$ for $x \geq 0$ 
would expose this regression.
Industrial experience reports suggest that property-based testing 
often uncovers edge cases and boundary conditions missed by unit tests~\cite{hughes_2016_experiences,goldstein_2024_pbt_practice}.
Adoption, however, remains limited because writing property-based tests 
requires manual effort to define both input constraints and suitable properties,
a task practitioners find challenging~\cite{goldstein_2024_pbt_practice}.
This motivates research into transformation approaches
that automatically generalize existing unit tests by deriving properties from program semantics.

We propose a semantics-based approach for automated test generalization
that analyzes both test and implementation code
to derive path-exact specifications through single-path symbolic analysis~\cite{pasareanu_2013_symbolic}.
Our method determines which inputs follow the same execution path as existing tests
and transforms unit tests into property-based tests
that validate the same assertions across entire input partitions.
Because specifications are extracted from program semantics,
the resulting properties are exact for the analyzed implementation along each execution path.
The generalized test retains the original assertion,
agrees with its expected value at the original inputs,
and checks the assertion across additional inputs from the same execution path to detect later regressions.
Test generation tools such as \ToolEvoSuite{}~\cite{fraser_2011_evosuite} and Randoop~\cite{pacheco_2007_randoop}
instead create new tests and infer their regression assertions from the observed behavior of the implementation.
Generalization requires existing tests, whereas generation creates them,
so the two techniques are complementary:
generalization can follow generation when developer-written tests are absent.
To our knowledge, JARVIS~\cite{peleg_2018_jarvis} is the only prior work
that automatically generalizes unit tests into property-based tests.
However, JARVIS infers properties from input-output examples based solely on test code,
relying on predefined abstraction templates that yield overapproximations.
In contrast, our white-box approach leverages both static and dynamic program analysis
to extract exact specifications for the execution paths exercised by the original tests.

We implemented this approach in \ToolTeralizer{}, a prototype tool for Java
that transforms JUnit tests into property-based \ToolJqwik{}~\cite{link_2022_jqwik} tests.
\ToolTeralizer{} employs a five-stage pipeline:
(1)~analyzing tests and their assertions regarding suitability for generalization,
(2)~identifying tested methods through data-flow analysis,
(3)~extracting specifications through single-path symbolic analysis~\cite{pasareanu_2013_symbolic},
(4)~creating generalized property-based tests, and
(5)~filtering generalized tests to retain only those that improve fault detection capability.
Figure~\ref{fig:generalization} illustrates the effects of this transformation,
showing how a simple equality assertion $abs(0) = 0$
becomes the property $abs(x) = x$,
valid for all non-negative values of $x$.

We evaluate \ToolTeralizer{} in three complementary environments
that span controlled to real-world conditions.
The \DatasetEqBench{} benchmark~\cite{badihi_2021_eqbench} provides numeric-focused programs
well suited to symbolic analysis. Because it lacks tests,
we generate them with \ToolEvoSuite{}~\cite{fraser_2011_evosuite}.
Utility methods from Apache Commons provide an intermediate setting
in which we compare generated and developer-written tests on the same codebase.
Finally, \TzRealworldEligibleProjects{} eligible Java projects with developer-written tests
from the RepoReapers dataset~\cite{munaiah_2017_reporeapers}
expose practical applicability barriers.
We also compare \ToolTeralizer{} with the results JARVIS reports
for the 12 benchmark projects of its original evaluation.

The results show broader measured applicability than JARVIS on the shared benchmark:
\ToolTeralizer{} produces generalized tests in 9 of 12 projects,
whereas JARVIS reports success in 2 of 12 projects.
Under controlled conditions, generalization increases mutation scores
by \TzEffectivenessEqbenchEvosuiteMutationImprovementMinPp{}--\TzEffectivenessEqbenchEvosuiteMutationImprovementMaxPp{}~percentage points
on \ToolEvoSuite{}-generated tests for \DatasetEqBench{}
and by \TzEffectivenessCommonsEvosuiteMutationImprovementMinPp{}--\TzEffectivenessCommonsEvosuiteMutationImprovementMaxPp{}~percentage points
on generated Apache Commons tests.
For mature developer-written Apache Commons tests, the increase is only
\TzEffectivenessCommonsDeveloperMutationImprovementMinPp{}--\TzEffectivenessCommonsDeveloperMutationImprovementMaxPp{}~percentage points
from a baseline of \TzEffectivenessCommonsDeveloperBaselineMutationScorePct{}.
Under real-world conditions, \TzRealworldApplicabilityProjects{} of
\TzRealworldEligibleProjects{} eligible RepoReapers projects complete all five stages,
yielding \TzRealworldGeneralizationsFinalUsable{} generalized tests that pass through mutation testing.
The associated exclusions arise primarily from prototype and project-integration limitations,
insufficient evidence for sound generalized oracles,
and build, execution, or environment failures.

This paper makes the following contributions:

\begin{enumerate}
\item A \textbf{semantics-based test generalization approach} that extracts path-specific specifications through symbolic analysis and transforms conventional unit tests into property-based tests.
\item A Java \textbf{prototype implementation}, \ToolTeralizer{}, that realizes the approach as a five-stage pipeline.
\item A comprehensive \textbf{empirical evaluation} that compares against JARVIS's published benchmark results and measures effectiveness, efficiency, and applicability from controlled benchmarks to real-world projects.
\item A systematic \textbf{analysis of applicability barriers} that distinguishes prototype and integration limitations, insufficient specification evidence, and environmental failures.
\item An \textbf{open implementation and replication package}~\cite{replicationpackage} that supports reproducing and extending the results.
\end{enumerate}

The paper is organized as follows.

Section~\ref{sec:evaluation} evaluates the approach through seven research questions:
the JARVIS comparison (RQ0), mutation score effects (RQ1 and RQ2),
test suite size and runtime (RQ3), efficiency relative to test generation (RQ4),
and causes of unsuccessful generalization under controlled and real-world conditions (RQ5 and RQ6).
Section~\ref{sec:discussion} discusses the results, future directions, and threats to validity.
Section~\ref{sec:related-work} positions the approach within the broader testing literature,
and Section~\ref{sec:conclusions} concludes the paper.
